# FWIGAN validation record

**Status at 2026-10-12:** The research toolkit has passing hosted CPU checks and a complete passing RTX 4090 package test suite. The separate equivalent-work CUDA benchmark **failed numerical parity** on tiny-clean training; no CUDA speedup, capacity, timing or memory result is accepted. Pull request #1 remains a draft. The newer opt-in CUDA repeatability diagnostic has not run on a GPU because Pod creation failed before allocation. These are different validation stages.

This is shared-host tiny CPU evidence, not GPU or full-scale performance; see [measurement details](../performance.md).

## GPU numerical limits

The CUDA comparator retains its `atol + rtol × abs(package value)` rule for all fields except recovered velocity change. For `physical_changes.velocity` only, each float32 cell has a one-local-model-ULP floor: `m = max(abs(common velocity), abs(original final velocity), abs(package final velocity))`, `q = nextafter_float32(m, +∞) − m`, and the bound is `max(atol + rtol × abs(package change), q)`. CPU comparisons remain exact; full velocity, source/sigma, critic, gradients, Adam, schedulers/scalers and RNG retain their existing checks. In the failed 2,800-cell comparison, **539** cells failed the old bound, the floor rescued **17**, and **522 still failed**. This narrow resolution allowance did not make a material disagreement pass.

The pinned DeepWave 0.0.9 CUDA source uses shared-cell `atomicAdd` accumulation for model gradients across shot blocks. Its reduction order may vary despite cuDNN deterministic settings and restored RNG. Critic AMP or max-pool operations may amplify small changes, but **the cause of the observed divergence remains unproven**. A checkpoint restores registered physical/optimizer/scheduler/scaler state and random streams; it does not promise a bit-exact GPU trajectory.

The opt-in `f54f251` repeatability mode replays the same calibrated tiny-clean state three times for two epochs, comparing original/package and same-kind repeats. The optional cuDNN-TF32-off pass is a labelled ablation. It is **untimed** and cannot validate performance, even if it completes. The focused 19-test CPU check and real two-profile CPU smoke passed; the planned CUDA attempt failed `POST /pods` with HTTP 500 before a Pod existed. Three fresh account lists found no owned Pod, and the subsequent RTX 4090 public catalog showed no positive capacity in ten regions. No GPU diagnostic result is claimed. See the [performance guide](../performance.md#cuda-measurement) for the command.

## Audit and remaining work

All seven uniquely created package-validation Pods were deleted and their cleanup verified; [cleanup summary](pod-cleanup.json) records IDs and scope. Their combined **$0.452048** duration × reported-rate estimate excludes earlier legacy notebook tests and is **not a billing invoice**. Failed pre-create requests created no Pod and have no compute estimate.

An accepted CUDA comparison still requires all workloads to pass numerical, successful-update and RNG gates with complete synchronized raw timing samples, native solver counts and absolute/incremental allocated/reserved peaks. Only then should `examples/plot_gpu_benchmark.py` render a chart. Full Marmousi inversion/convergence, general GPU speedup and a modern DeepWave backend remain unverified. The [machine-readable summary](validation-summary.json) and [review decisions](review.md) preserve the evidence boundary.
